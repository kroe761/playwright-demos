addLocatorHandler()

Pain
TypeScript

// Cookie banner blocks every test

  .click(); // fails if banner reappears
Java

    .click(); // fails if banner reappears

One new popup = copy-pasting dismiss logic into every test that touches that page.

Cookie banners, newsletter popups, interstitials block every test. Most teams copy-paste dismiss logic into every test or wrap in try/catch.

addLocatorHandler()

TypeScript

await page.addLocatorHandler(
  page.getByText('Accept all'),
  async (locator) => await locator.click()
);
// runs on every navigation, automatically
Java

page.addLocatorHandler(
  page.getByText("Accept all"),
  locator -> locator.click()
);
// runs on every navigation, automatically
One line. Stack multiple handlers for sites with several popups.
addLocatorHandler registers a handler that fires whenever that locator appears — on any page, any navigation. Universal pain, one-line fix.

Web-first assertions vs. page.waitforTimeout()

Pain
TypeScript

await saveButton.click();
await page.waitForTimeout(2000); // 🤞

// Jest/Vitest — point-in-time, no retry
Java

// JUnit — point-in-time, no retry

Too short = flaky. Too long = slow. Usually both in the same suite.

Every Java Playwright suite has this. Arbitrary sleeps that are either too short (flaky) or too long (slow). Usually both in the same suite.
Act 1

Web-first assertions vs. page.waitForTimeout()

TypeScript

await saveButton.click();
await expect(successBanner)
  .toBeVisible(); // retries until true
// The assertion IS the wait.
Java

saveButton.click();
assertThat(successBanner)
    .isVisible(); // retries until true
// The assertion IS the wait.
Replace every sleep with the assertion itself. Faster AND flake-resistant.
Web-first assertions auto-retry for the full action timeout — default 5s. They're not a check, they're a wait. The assertion IS the wait. If you take nothing else from Act 1, take this.

page.waitForResponse()

Pain
TypeScript

await saveButton.click();
await page.waitForTimeout(1500); // hoping API responded
await expect(page.getByText('Saved')).toBeVisible();
Java

saveButton.click();
page.waitForTimeout(1500); // hoping API responded
assertThat(page.getByText("Saved")).isVisible();

You're guessing how long the API takes. The right number today is wrong on a slow CI box tomorrow.

Same problem as page.waitForTimeout() on DOM — but applied to network calls. You're guessing at a delay instead of waiting for the actual signal.
Act 1

page.waitForResponse()

TypeScript

const resp = await page.waitForResponse(
  '**/api/save',
  async () => await saveButton.click()
);
// returns the moment the response arrives
expect(resp.status()).toBe(200);
Java

Response resp = page.waitForResponse(
  "**/api/save",
  () -> saveButton.click()
);
// returns the moment the response arrives
assertThat(resp.status()).isEqualTo(200);
Same "wait for the actual signal" mindset — applied to network instead of DOM.
Wraps the action that triggers the request, returns when the matching response arrives. Zero guessing, zero sleeping. Also pairs with waitForRequest when you care about the outbound call.

page.route()

Mock your backend calls

TypeScript

await page.route('**/api/products',
  route => route.fulfill({
    status: 500,
    body: 'Internal Server Error'
  }));
// Also: abort(), continue() with overrides
Java

page.route("**/api/products",
    route -> route.fulfill(
        new Route.FulfillOptions()
            .setStatus(500)
            .setBody("Internal Server Error")));
// Also: abort(), continue() with overrides
Test every backend failure state without touching the backend.
fulfill() returns a canned response. abort() simulates a network failure. continue() with overrides rewrites the request in flight — rewrite URLs, inject headers, swap body fields. Most teams know fulfill and abort. The continue-with-overrides is the sleeper. Best way to test that your app can handle backend error states or edge cases

routeFromHAR()

Replay tests against a recorded backend

TypeScript

// Record once:
const context = await browser.newContext({
  recordHar: { path: 'fixtures/api.har' }
});
// Replay forever:
await context.routeFromHAR('fixtures/api.har',
  { notFound: 'fallback' });
Java

// Record once:
context = browser.newContext(
    new Browser.NewContextOptions()
        .setRecordHarPath(Paths.get("fixtures/api.har")));
// Replay forever:
context.routeFromHAR(Paths.get("fixtures/api.har"),
    new BrowserContext.RouteFromHAROptions()
        .setNotFound(RouteFromHARNotFound.FALLBACK));
Commit the HAR. Your backend becomes optional for UI tests.
(HTTP Archive file) Record real traffic once, commit the HAR to source control, replay it deterministically in CI. Pairs with setOffline for fully hermetic tests. The update:true flag lets you refresh periodically without manual recording.

page.clock

Control time in your tests

TypeScript

// Freeze time at a specific moment
await page.clock.setFixedTime(
  new Date('2024-12-31T23:59:55Z'));
await page.goto('https://example.com/countdown');

// Fast-forward 10 seconds
await page.clock.fastForward(10_000);
Java

// Freeze time at a specific moment
page.clock().setFixedTime(
    Instant.parse("2024-12-31T23:59:55Z"));
page.navigate("https://example.com/countdown");

// Fast-forward 10 seconds
page.clock().fastForward(10_000);
Test session expiry, countdowns, and scheduled jobs without waiting.
Your session expires after thirty minutes? Fast-forward thirty-one. Countdown timer? Freeze it at T-minus-five seconds and assert on the warning UI. This covers all the JavaScript time APIs. No more waiting in real time, and no more mocking Date in your app code just to make your tests work.

Backend Through the Browser

Flip the direction — use Playwright to reach the backend directly.
Real auth, real session, no UI setup chain.

Act 3 flips the direction. Instead of isolating the frontend from the backend, we use the browser to reach the backend — borrow its session, its CSRF token, its auth state. Most tools can't do this. Playwright can, because it has a real browser and a real HTTP client in the same process.
Act 3

API-seeded fixtures

Skip the UI setup chain

TypeScript

const api = await request.newContext({
  baseURL: process.env.BASE_URL
});

await api.post('/api/users', { data: { 
    email: 'test@example.com', 
    plan: 'enterprise' 
  }});

await page.goto('/dashboard');
Java

APIRequestContext api = playwright.request()
    .newContext(new APIRequest.NewContextOptions()
        .setBaseURL(System.getenv("BASE_URL")));

api.post("/api/users",
    RequestOptions.create().setData(Map.of(
        "email", "test@example.com",
        "plan",  "enterprise")));

page.navigate("/dashboard");
Skip the UI setup chain. Tests that took 30s of clicks take 200ms.
APIRequestContext is a full HTTP client baked into Playwright. Key point: you're calling an endpoint that already exists — /api/users, /api/orders, whatever your app already has. No new backend work required. Skips the "navigate, click, fill, submit" setup chain.

Reuse your session across tests

Log in once. Never log in again.

TypeScript

// Global setup — log in, then save:
await context.storageState({ path: 'auth.json' });

// Every test — start already authenticated:
const context = await browser.newContext({
  storageState: 'auth.json'
});
Java

// Global setup — log in, then save:
context.storageState(
  new BrowserContext.StorageStateOptions()
    .setPath(Paths.get("auth.json")));

// Every test — start already authenticated:
BrowserContext context = browser.newContext(
    new Browser.NewContextOptions()
        .setStorageStatePath(Paths.get("auth.json")));
Log in once per suite run. Every test starts already authenticated.
Saves Cookies and LocalStorage storageState() saves cookies and localStorage to a file. Load it into any new context and that context is already logged in — no UI login flow, no API call, just the session. Commit auth.json to your test fixtures or regenerate it in CI setup. If your app uses localStorage tokens, this catches those too — not just cookies.

For more complicated auth...

Browser login → scrape what you need → call the backend directly

TypeScript

// Scrape CSRF and session cookie
const csrf = await page.evaluate(() => document.querySelector('meta[name="csrf-token"]').content);
const session = (await context.cookies()).find(c => c.name === 'session');

// Set CSRF and Session on the api context
const api = await request.newContext({
  baseURL: process.env.BASE_URL,
  extraHTTPHeaders: { 'X-CSRF-Token': csrf, 'Cookie': `session=${session.value}` }
});

// Hit the backend directly — no more UI
const resp = await api.get('/api/account/settings');
expect(resp.status()).toBe(200);
Let me walk through each step. First, a real browser login — no mocking, no token injection, an actual session. Then page.evaluate() reaches into the live DOM to grab the CSRF token. context.cookies() finds the session cookie and passes it straight to APIRequestContext — no file needed. And from here the browser is out of the picture; these are pure HTTP calls carrying real auth.

Observer patterns

TypeScript

// JS console errors
page.on('console', msg => {
  if (msg.type() === 'error')
    errors.push(msg.text());
});
// Unhandled exceptions
page.on('pageerror', err =>
  failures.push(err.message));
// Failed network requests
page.on('requestfailed', req =>
  networkFailures.push(
    `${req.url()} — ${req.failure()}`));

expect(errors).toHaveLength(0);
Java

// JS console errors
page.onConsoleMessage(msg -> {
    if (msg.type().equals("error"))
        errors.add(msg.text());
});
// Unhandled exceptions
page.onPageError(err ->
    failures.add(err.message()));
// Failed network requests
page.onRequestFailed(req ->
    networkFailures.add(
        req.url() + " — " + req.failure()));

assertThat(errors).isEmpty();
Catches "passing test, silently broken app." Wire once, benefit everywhere.
Here's the problem this solves: a test can pass green while the page is throwing JavaScript errors, failing XHRs, and swallowing unhandled exceptions — because you never asserted on any of them. Wire these three listeners once in your base class, and every one of those signals becomes part of your failure context automatically.
