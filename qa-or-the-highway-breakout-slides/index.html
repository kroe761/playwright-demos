Locator composition

Pain

// Goal: delete the "Widget A" row
await page.locator(
  "//table[@id='inventory']/tbody/tr[3]/td[6]/button"

// "row 3" ...until someone inserts a row

You wanted the "Widget A" row — but you hard-coded row 3, cell 6. Insert a row or add a column and it points at the wrong thing.

Act 1

Locator composition

TypeScript

await page.getByRole('row')
  .filter({ hasText: 'Widget A' })
  .getByRole('button', { name: 'Delete' })
  .click();
Java

page.getByRole(ROW)
    .filter(new Locator.FilterOptions()
        .setHasText("Widget A"))
    .getByRole(BUTTON,
        new Page.GetByRoleOptions()
            .setName("Delete"))
    .click();

filter() · and() · or() · nth() · first() · last()

Reads like a sentence. Survives refactors that break CSS selectors.
  • getByRole('row') → grab all the row elements
  • .filter(hasText: 'Widget A') → keep the first one containing "Widget A"
  • .getByRole('button', name: 'Delete') → the Delete button inside that row
  • .click()
  • Targets content, not position → no row/column index to break

routeFromHAR()

Replay tests against a recorded backend

TypeScript

// Record once:
const context = await browser.newContext({
  recordHar: { path: 'fixtures/api.har' }
});
// Replay forever:
await context.routeFromHAR('fixtures/api.har',
  { notFound: 'fallback' });
Java

// Record once:
context = browser.newContext(
    new Browser.NewContextOptions()
        .setRecordHarPath(Paths.get("fixtures/api.har")));
// Replay forever:
context.routeFromHAR(Paths.get("fixtures/api.har"),
    new BrowserContext.RouteFromHAROptions()
        .setNotFound(RouteFromHARNotFound.FALLBACK));
Commit the HAR. Your backend becomes optional for UI tests.
  • HAR = HTTP Archive (a recording of traffic)
  • Record once → commit → replay forever, deterministic
  • Backend becomes optional; + setOffline = hermetic
  • update flag re-records when the API changes

TypeScript

// Global setup — log in, then save:

  storageState: 'auth.json'

    .setPath(Paths.get("auth.json")));

For more complicated auth...

Browser login → scrape what you need → call the backend directly

TypeScript

// Scrape security token and session cookie
const token = await page.evaluate(() => document.querySelector('meta[name="security-token"]').content);
const session = (await context.cookies()).find(c => c.name === 'session');

// Set security token and session on the api context
const api = await request.newContext({
  baseURL: process.env.BASE_URL,
  extraHTTPHeaders: { 'X-Security-Token': token, 'Cookie': `session=${session.value}` }
});

// Hit the backend directly — no more UI
const resp = await api.get('/api/account/settings');
expect(resp.status()).toBe(200);
Java

// Scrape security token and session cookie
String token = (String) page.evaluate("document.querySelector('meta[name=\"security-token\"]').content");
Optional<Cookie> session = context.cookies().stream()
    .filter(c -> c.name.equals("session")).findFirst().orElseThrow();

// Set security token and session on the api context
APIRequestContext api = playwright.request().newContext(
    new APIRequest.NewContextOptions()
        .setBaseURL(System.getenv("BASE_URL"))
        .setExtraHTTPHeaders(Map.of("X-Security-Token", token, "Cookie", "session=" + session.value)));

// Hit the backend directly — no more UI
APIResponse resp = api.get("/api/account/settings");
assertThat(resp.status()).isEqualTo(200);
  • For custom-header or token-based auth
  • Real browser login (not mocked, not injected)
  • page.evaluate → security token from the DOM · context.cookies → session
  • Hand both to API context → browser gone, pure authed HTTP

Observer patterns

TypeScript

// JS console errors
page.on('console', msg => {
  if (msg.type() === 'error')
    errors.push(msg.text());
});
// Unhandled exceptions
page.on('pageerror', err =>
  failures.push(err.message));
// Failed network requests
page.on('requestfailed', req =>
  networkFailures.push(
    `${req.url()} — ${req.failure()}`));
expect(errors).toHaveLength(0);
Java

// JS console errors
page.onConsoleMessage(msg -> {
    if (msg.type().equals("error"))
        errors.add(msg.text());
});
// Unhandled exceptions
page.onPageError(err ->
    failures.add(err.message()));
// Failed network requests
page.onRequestFailed(req ->
    networkFailures.add(
        req.url() + " — " + req.failure()));
assertThat(errors).isEmpty();
Catches "passing test, silently broken app." Wire once, benefit everywhere.
  • Passing test, silently broken app — you never asked
  • Wire 3 listeners once in base class: console error / pageerror / requestfailed
  • Assert zero, or attach to failure output
  • Cheapest insurance in the talk

  • Relay (Node, :8080) = the hub: fans IN frames from every test, fans OUT to viewers
  • Dashboard (React, :5173) subscribes over WS, renders one tile per test, updates live
  • Fully decoupled — tests don't know the dashboard exists; they just publish to the relay
  • Why a relay? tests are ephemeral & parallel; the relay is the one stable address the dashboard connects to
  • Scales both ways: many tests in, many viewers out
  • 3 processes, that's the whole system
  • A live tile per running test
  • See what every browser is doing, right now

How it works

TypeScript

// Open a websocket connection
const name = encodeURIComponent(testInfo.title);
const ws = new WebSocket(
  `ws://localhost:8080?name=${name}`
);

// Send the screencast to the websocket
await page.screencast.start({
  onFrame: (frame) => ws.send(frame.data),
  path: 'recording.webm',
  quality: 50,
  size: { width: 1280, height: 720 },
});
Java

// Open a websocket connection
var url = "ws://localhost:8080?name=" + testName;
var ws = new WsClient(url);
ws.connect();

// Send the screencast to the websocket
page.screencast().start(
  new Screencast.StartOptions()
    .setOnFrame(f -> ws.send(f.getData()))
    .setPath(Paths.get("recording.webm"))
    .setQuality(50)
    .setSize(new ViewportSize(1280, 720))
);
