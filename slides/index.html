Why Playwright can do this

Playwright doesn't talk to the browser through WebDriver. It talks through DevTools Protocol — the same channel Chrome DevTools uses. That's why downloads, network interception, console events, and trace recording are first-class APIs here and not in your Selenium suite.

Selenium 4 added a CDP escape hatch — Chrome-only, outside the WebDriver standard.

Plant this early. It pre-empts the "can't Selenium do that?" Q&A. Every feature we see today exists because of this architectural decision. When you see something that looks impossible for a test framework, remember: Playwright is using the same channel as your browser's devtools.

Act 1

addLocatorHandler()

Pain

// Cookie banner blocks every test
// You copy-paste dismiss logic everywhere
page.getByText("Accept all").click();
page.getByRole(BUTTON, name("Subscribe"))
    .click(); // fails if banner appears
Fix

page.addLocatorHandler(
  page.getByText("Accept all"),
  locator -> locator.click()
);
// now runs on every navigation, automatically
One line. Stack multiple handlers for sites with several popups.
Pain: cookie banners, newsletter popups, interstitials block tests. Most teams handle this by copy-pasting dismiss logic into every test, or by wrapping in try/catch. addLocatorHandler registers a handler that fires whenever that locator appears — on any page, any navigation. Universal pain, one-line fix.
Act 1

Locator composition

Pain

// CSS nth-child gymnastics
page.locator("table tr:nth-child(3) td:nth-child(2) button")
    .click();
// Breaks on every UI change
Fix

page.getByRole(ROW)
    .filter(new Locator.FilterOptions()
        .setHasText("Widget A"))
    .getByRole(BUTTON,
        new Page.GetByRoleOptions()
            .setName("Delete"))
    .click();

filter() · and() · or() · nth() · first() · last()

Reads like a sentence. Survives refactors that break CSS selectors.
The submit button inside the row that contains "Widget A" — that's a completely natural English description. Locator composition makes it Java too. This is the biggest sleeper in Act 1 for experienced teams. They've been writing nth-child selectors for years without knowing filter() exists.
Act 1

Web-first assertions vs. Thread.sleep

Pain

saveButton.click();
Thread.sleep(2000); // 🤞
assertThat(successBanner)
    .isVisible();
Fix

saveButton.click();
assertThat(successBanner)
    .isVisible(); // retries until true
// The assertion IS the wait.
Replace every Thread.sleep with the assertion itself. Faster AND flake-resistant.
This is the single biggest win for most Java Playwright suites. Web-first assertions auto-retry for the full action timeout — default 5 seconds. They're not a check, they're a wait. The assertion IS the wait. If you take nothing else from Act 1, take this. Side-by-side demo — show a test with Thread.sleep, rewrite it live.
Act 1

page.waitForResponse()

Pain

saveButton.click();
Thread.sleep(1500); // hoping API responded
assertThat(page.getByText("Saved"))
    .isVisible();
Fix

Response resp = page.waitForResponse(
  "**/api/save",
  () -> saveButton.click()
);
// returns the moment the response arrives
assertThat(resp.status()).isEqualTo(200);
Same "wait for the actual signal" mindset — applied to network instead of DOM.
waitForResponse is waitForResponse: it wraps the action that triggers the request, and returns when the matching response arrives. Zero guessing, zero sleeping. Works identically in all four bindings. Also pairs with waitForRequest when you care about the outbound call.

Isolating the Layers

Two directions:

  • Direction A — frontend isolated from backend
  • Direction B — backend isolated from frontend

"Your frontend is the most authoritative documentation your backend has — and Playwright lets you read it at runtime."

Act 2 has a narrative turn. First half: isolate the frontend from the backend — test UI behavior without a working backend. Second half: flip it — isolate the backend from the frontend. Most tools can do one or the other. Playwright does both.
Act 2 · Dir A

page.route()


// Simulate any backend state from one primitive
page.route("**/api/products", route -> route.fulfill(
    new Route.FulfillOptions()
        .setStatus(500)
        .setBody("Internal Server Error")));

// Also: abort(), continue() with overrides, slow responses

Four failure modes from one feature: 500s · network failures · slow responses · malformed payloads

Test every backend failure state without touching the backend.
fulfill() returns a canned response. abort() simulates a network failure. continue() with overrides rewrites the request in flight — rewrite URLs, inject headers, swap body fields. Most teams know fulfill and abort. The continue-with-overrides is the sleeper.
Act 2 · Dir A

routeFromHAR()


// Record once:
context = browser.newContext(new Browser.NewContextOptions()
    .setRecordHarPath(Paths.get("fixtures/api.har")));

// Replay forever:
context.routeFromHAR(Paths.get("fixtures/api.har"),
    new BrowserContext.RouteFromHAROptions()
        .setNotFound(RouteFromHARNotFound.FALLBACK));
Commit the HAR. Your backend becomes optional for UI tests.
Record real traffic once, commit the HAR to source control, replay it deterministically in CI. Pairs with setOffline for fully hermetic tests. The update:true flag lets you refresh periodically without manual recording.
Act 2 · Dir A

page.clock


// Freeze time at a specific moment
page.clock().setFixedTime(Instant.parse("2024-12-31T23:59:55Z"));
page.navigate("https://example.com/countdown");

// Fast-forward 10 seconds
page.clock().fastForward(10_000);

// Covers Date.now(), setTimeout, setInterval, requestAnimationFrame
Test session expiry, countdowns, and scheduled jobs without waiting.
Session expires after 30 minutes? Fast-forward 31 minutes. Countdown timer? Freeze at T-5 seconds, assert the warning UI. Covers all JS time APIs. No more waiting in real time, no more mocking Date in your app code just to make tests work. Verify Java parity against your pinned version before this demo.

context.setOffline(true)


// Flip one bit
context.setOffline(true);
page.reload();
assertThat(page.getByText("You're offline")).isVisible();

// Toggle mid-test to test reconnection
context.setOffline(false);
assertThat(page.getByText("Back online")).isVisible();
Offline UX is one line away. Test reconnection flows in CI.
Most teams have never tested their offline state because it seemed hard. It's one method call. Pair with routeFromHAR for a fully hermetic offline test — no real network traffic at all.

Environment emulation


// iPhone 13 · Japanese locale · Tokyo timezone ·
// Shibuya geolocation · dark mode — in one config block
BrowserContext ctx = browser.newContext(new Browser.NewContextOptions()
    .setViewportSize(390, 844)
    .setUserAgent("Mozilla/5.0 (iPhone; CPU iPhone OS 16_0 ...)")

The leverage gap here: most teams run default desktop English UTC because they assume everything else needs infrastructure they don't have. They don't. This is a block of NewContextOptions. Combine with playwright.devices() descriptors for a shorthand.
Act 2 · Dir B

API-seeded fixtures


// Before: navigate → click → fill → submit (slow, fragile)
// After: seed state directly via API
APIRequestContext api = playwright.request().newContext(
    new APIRequest.NewContextOptions().setBaseURL("http://localhost:3000"));

api.post("/api/test-fixtures",
    RequestOptions.create().setData(Map.of(
        "userId", "test-user-42",
        "plan",   "enterprise")));

// Now navigate to the page that needs this state
page.navigate("/dashboard");
Skip the UI setup chain. Tests that took 30s of clicks take 200ms.
APIRequestContext is a full HTTP client baked into Playwright. You can call your backend directly to create state, then test the UI that depends on that state. Skips the "navigate, click, fill, submit" setup chain. This is the intro to the wow.

Act 3

Observer patterns


// Wire once in your base test class
page.onConsoleMessage(msg -> {
    if (msg.type().equals("error"))
        errors.add(msg.text());
});
page.onPageError(err -> failures.add(err.message()));
page.onRequestFailed(req ->
    networkFailures.add(req.url() + " — " + req.failure()));

// Assert at end of test
assertThat(errors).isEmpty();
Catches "passing test, silently broken app." Wire once, benefit everywhere.
The problem this solves: a test can pass green while the page has JS errors, failed XHRs, unhandled exceptions — because you never asserted on any of them. Wire these three listeners once in your base class. Surface every signal as part of the failure context automatically. ~90s slot.
